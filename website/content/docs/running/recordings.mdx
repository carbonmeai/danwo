Every test keeps a **flight record**: a video, each step, the page's console and network, and every
call and webhook behind it. In the dashboard it opens over the page you came from.

## Open one

Click a test, a run's row or a matrix cell. The recording opens on top, and Esc closes it.

![A recording: the steps on the left, the video and its tabs on the right](/docs/dashboard-recording.png)

On the left are the steps. Each has **Go to**, which moves the video to that step. Under them are
the error, where the test stopped, the faults and any lint findings.

## Read the checks

After the steps comes **Checks**: what ran once the browser was done. First, the wait for
background work, such as webhooks and Inngest runs, with how long it took and what it waited for.
Then each check your invariant made, with a ✓ or ✗.

```ts title="tests/checkout.danwo.ts (fragment)"
}).invariant(async ({ app, stripe, expect }) => {
  expect(await grantedCredits(app.baseUrl, "u1"), "credits granted").toBe(500)
})
```

This check shows as `expect(credits granted).toBe(500)` with the value it got. When it fails, it
shows what it wanted too. Give a check a message, as above, so its row reads well.

## Skip the idle tail

The browser sits still while danwo waits and checks. The scrubber shades these stretches as
"settling" and "checks", each with a **Go to** button. The video plays through them at 4× by
default; turn off **Idle at 4×** to watch them at normal speed.

## The tabs

| Tab            | What it shows                                                                        |
| -------------- | ------------------------------------------------------------------------------------ |
| Replay         | the video, with steps, faults, settling and checks marked on the scrubber            |
| Console        | the page's console, filtered by level                                                |
| Network        | the page's own requests                                                              |
| Providers      | a waterfall of steps, provider calls, webhooks and faults; then the calls as a table |
| Emulator state | what each emulator held when the test ended                                          |
| Effects        | what each step was expected to change, and what it did                               |
| Matrix         | on a trial: the fault it ran under, and its verdict                                  |

## Read the calls behind a step

The **Providers** tab lines up every call with the step that caused it:

![The Providers tab: a waterfall of the test's steps and calls, with Stripe answering 500](/docs/dashboard-providers.png)

Click a call to see its request and response. Secrets are redacted before the record is written,
so they never reach the page.

## Copy a prompt to fix it

**Copy prompt to fix** copies the failure as a prompt for a coding agent: what failed, where, the
calls and faults around it. The menu next to it copies the same page as Markdown.

## Link to a moment

| Address part      | Opens                         |
| ----------------- | ----------------------------- |
| `?open=<record>`  | that recording                |
| `&pane=providers` | that tab                      |
| `&t=12.5`         | the video 12.5 seconds in     |
| `#step-3`         | the video where step 3 starts |

## What's kept

| Setting                      | Kept                                        |
| ---------------------------- | ------------------------------------------- |
| `record: "always"` (default) | every run's flight record                   |
| `record: "on-failure"`       | only failed runs'                           |
| `record: { keepRuns: 50 }`   | how many of the newest runs keep recordings |
| `video: "on"` (default)      | a video with every record                   |
| `video: "retain-on-failure"` | videos of runs that didn't pass             |
| `video: "off"`               | no video                                    |

Older runs' recordings are deleted as each run finishes. `danwo test --keep-runs 200` keeps more
for one run. The run summaries the dashboard lists stay longer (200 runs), so an old run's row
reads **recording deleted** and its Watch button is turned off.

## How much disk it takes

A browser test's video is usually 50 to 250 KB. A run's folder, with its videos, screenshots and
records, is typically under 1 MB for a small suite and grows with the number of tests. Fifty runs
of a 20-test suite come to tens of megabytes. Mobile screen recordings are larger; turn video to
`"retain-on-failure"` to keep only the ones you'll watch.

```ts title="danwo.config.ts · recordings"
record: { mode: "always", keepRuns: 100 },
video: "retain-on-failure",
```

<Callout type="warn">
  Video shows the screen as it was. Fields holding a secret show as dots, but a secret your app
  prints as text is on screen. Use `video: "off"` for suites that show one.
</Callout>
