This page takes you from nothing to a passing UI test you can watch back, in about five minutes.
The short path is three commands and one test file, with no providers, keys or model.

You need Node.js 22.22.3 or a later 22, or 24.11.1 or newer, and an app you can start with a
command, such as `npm run dev`. On any other Node, danwo stops and says which version it found.
The app itself can run on Node 20 or later ([the app's Node](/docs/node-preload#your-apps-node-version)).

danwo runs on macOS, Linux and Windows. Mobile tests need macOS or Linux: the iOS Simulator only runs on a Mac, and Android emulators on Windows are not checked yet.

<Steps>
<Step>

### Run `danwo init`

In your app's folder:

<Tabs items={["npm", "pnpm", "bun"]}>
  <Tab value="npm">

```sh
npx @danwo/cli init
```

  </Tab>
  <Tab value="pnpm">

```sh
pnpm dlx @danwo/cli init
```

  </Tab>
  <Tab value="bun">

```sh
bunx @danwo/cli init
```

  </Tab>
</Tabs>

It looks at your project first: the package manager, the framework, the command that starts
your app, and the services your code uses. Then it asks four things:

| Question                                | For a UI-only start     | What it means                                                  |
| --------------------------------------- | ----------------------- | -------------------------------------------------------------- |
| What should tests drive?                | **Web** (or **Mobile**) | A browser, an Android app, both, or only your app's API.       |
| Which model should agent steps use?     | **None**                | The AI that runs plain-English steps. You can add one later.   |
| Which providers should danwo emulate?   | untick them all         | Services found in your code (Stripe, Resend…) come pre-ticked. |
| Which coding agents should learn danwo? | any                     | Claude Code, Cursor or Codex get danwo's skill and MCP server. |

To skip the questions, pass the answers:

```sh
npx @danwo/cli init --yes --engine web --model-source none --providers none
```

When it's done, it shows what it wrote:

```text
Files
  created   danwo.config.ts
  created   tests/example.danwo.ts
  updated   package.json        (adds test:danwo)
  created   .gitignore          (.danwo/)
```

It also installs `@danwo/cli` and `@danwo/sdk`, and the Chromium build danwo drives. With a model
picked, it adds the model's key to `.env.example` too.

On a new machine, or after `--skip-install`, install the browser yourself:

```sh
npx @danwo/cli install-browser
```

On Linux, add `--with-deps` for the system libraries.

In a monorepo, run init in the app's own folder. It finds the workspace (pnpm, npm, Yarn or Bun)
and adds the packages to the app's `package.json` with the workspace's package manager.

Then run danwo through the app's `test:danwo` script. npx looks for commands from the workspace
root, and Bun and pnpm link the `danwo` command into the app's folder only. When you do use npx,
always give it the full package name, `@danwo/cli`: the unscoped name belongs to someone else.

</Step>
<Step>

### Write a UI test

Add a test that does what a user does. Change the page, the labels and the text to match your
app:

```ts title="tests/sign-up.danwo.ts"
import { test } from "@danwo/sdk"

test("signs up", async ({ app, screen, expect }) => {
  await app.open("/sign-up")
  await screen.getByLabel("Email").fill("ada@example.com")
  await screen.getByLabel("Password").fill("correct horse battery staple")
  await screen.getByRole("button", { name: "Create account" }).click()

  await expect(screen.getByRole("heading", { name: "Welcome, Ada" })).toBeVisible()
})
```

A test gets **fixtures**: ready-made objects passed in by name. `app` is your running app,
`screen` finds things on the page, and `expect` checks them. Checks wait for the page, so you
never write sleeps. [Agent and locators](/docs/agent-and-locators) lists every way to find an
element.

</Step>
<Step>

### Run it

```sh
npm run test:danwo
```

danwo starts your app, opens a fresh browser and runs every test in `tests/`:

```text
Running 2 tests with 1 worker

  ✓ tests/example.danwo.ts › the home page opens 812 ms, worker 0
  ✓ tests/sign-up.danwo.ts › signs up 1.4 s, worker 0

2 passed
report: .danwo/runs/20261020-091203-ab12/report.html
```

`tests/example.danwo.ts` is the test init wrote: it checks that your home page answers and opens.

</Step>
<Step>

### Watch it in the dashboard

```sh
npx @danwo/cli serve --open
```

The dashboard opens at `http://127.0.0.1:4310`. Click a test to open its recording:

- **Replay:** a video of the run, with a jump to each step.
- **Console** and **Network:** what the page logged and requested.

</Step>
</Steps>

That's a complete end-to-end setup. Everything below is optional.

## Read the config

`danwo.config.ts` says how to start your app. danwo runs your dev command itself, so it can put
the app behind its proxy:

```ts title="danwo.config.ts"
import { appEnvironment, defineConfig } from "@danwo/sdk"

const app = process.env.APP_URL ?? {
  command: "npm run dev",
  url: "http://localhost:3000",
}

export default defineConfig({
  testDir: "tests",
  workers: 1,
  timeout: 60_000,
  readiness: { mode: "page+backend", settle: true },
  environment: () => appEnvironment({ app, services: [] }),
})
```

`readiness` tells danwo to wait after each click until the page has settled **and** the calls it
caused have finished. `services` is empty: no provider is emulated yet.

## Later: write steps in plain English

Add a model to the config, and the `agent` fixture runs steps in plain English. Each is recorded
the first time it passes, then replayed with no model call:

```ts title="danwo.config.ts · the model"
model: "anthropic/claude-sonnet-5",
```

The key goes in `.env`, as `.env.example` shows. See [Agent steps](/docs/agent-steps).

## Later: emulate your providers

When your app calls Stripe, Resend or Clerk, list them in `services`. The proxy then answers
those hostnames with local emulators, with no sandbox keys and no code changes:

```ts title="danwo.config.ts · the environment"
environment: () => appEnvironment({ app, services: [stripeService(), resendService()] }),
```

The dashboard's **Providers** tab then shows every call your app made to them. [Test a
provider](/docs/test-a-provider) walks through a first check behind the screen.

<Callout type="warn">
  Setting `APP_URL` tests an app that's already running. That app wasn't started behind danwo's
  proxy, so its calls go to the **real** Stripe and Resend. Use it only with test keys. [Where danwo
  runs](/docs/where-danwo-runs) explains what works in each setup.
</Callout>
