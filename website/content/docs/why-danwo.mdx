danwo does what you expect of an end-to-end framework: locators, plain-English agent steps that
replay with no model calls, and visual comparison, on web, Android and iOS. For sign-up, log-in,
search and checkout screens, that is all you need.

Where it goes further is behind the screen. A page can say "Thank you" while Stripe charged the
card twice, or a webhook that arrived twice granted the credits twice. danwo is built to answer
those questions too, when your app has them.

## What is different

|                                          | danwo                                                                    | Typical end-to-end tools                   |
| ---------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------ |
| Drives the UI with locators and an agent | Yes, on web, Android and iOS                                             | Yes                                        |
| Replays with no model calls              | Yes: verified steps are cached as locators                               | Sometimes                                  |
| Visual comparison                        | Baselines, masks and thresholds, on web and devices                      | Often                                      |
| Third-party providers                    | Emulated, with real hostnames, state and signed webhooks                 | Real sandboxes, or mocks in the app's code |
| Judges the backend                       | Invariants over provider calls, webhooks and data                        | Pixels and DOM                             |
| Fault injection                          | A matrix planned from what the run called                                | No                                         |
| Races and data faults                    | Double-submits, concurrent users, Postgres and Redis faults, time travel | No                                         |
| Record of a failure                      | Steps, provider waterfall, effects diff, emulator state                  | Video and DOM                              |
| Where it runs                            | Your laptop and your CI, with your data                                  | Often a hosted service                     |

## The ideas behind it

**No app code changes.** The app runs as it does in production, pointed at an egress proxy by
environment variables. The proxy sends provider hostnames to danwo's emulators and everything else
where it was going. There are no test doubles to keep in sync with the code.

**Emulators, not mocks.** Each emulator keeps state across calls, signs its webhooks the way the
provider does, and answers with the error shapes the provider's SDK parses. `danwo fidelity` checks
them against the real APIs, so an emulator that drifts fails a check instead of passing your tests.

**Invariants judge the run, not the script.** A test's body says how a user gets somewhere; its
invariant says what must be true afterwards, whichever way the run went. That is what lets one
test be replayed under dozens of faults and still give a meaningful answer for each.

**Deterministic by default.** The agent's choices are recorded the first time and replayed after,
the emulators run on a clock danwo controls, and faults are applied one at a time. A failure under
a fault reproduces every time, which is what makes it worth fixing.
